# Spec: Migrate SQLAlchemy Query API to Session.execute(select()) Style

## Summary

This spec covers the migration of all SQLAlchemy legacy Query API calls (`session.query(...)`) to the modern `Session.execute(select(...))` style introduced as the preferred pattern in SQLAlchemy 1.4 and made the standard in SQLAlchemy 2.0. The expected outcome is a codebase free of legacy `Query` object usage, fully compatible with SQLAlchemy 2.0's execution model, and positioned to eliminate deprecation warnings generated by the legacy interface.

---

## Motivation

- **Legacy API deprecation:** The `Query` API was soft-deprecated in SQLAlchemy 1.4 and is a compatibility shim in SQLAlchemy 2.0. Continued reliance on it incurs deprecation warnings and blocks a clean upgrade path to SQLAlchemy 2.x.
- **Tech debt reduction:** The upgrade urgency is rated **medium**. The legacy Query API represents active tech debt that increases maintenance burden and reduces developer familiarity with the current SQLAlchemy idiom.
- **Forward compatibility:** The `Session.execute(select())` style is the only natively supported query pattern in SQLAlchemy 2.0+. Retaining `session.query()` calls requires the `legacy_query_interface` compatibility layer, which may be removed in a future release.
- **Deprecation warnings in CI:** SQLAlchemy 1.4 emits `LegacyAPIWarning` for Query API usage. These warnings pollute logs and, if treated as errors, cause CI failures.

> **Note:** Specific CVEs, EOL dates, and current pinned SQLAlchemy version are not provided in the tech analysis. See [Open Questions](#open-questions).

## Current State

The codebase currently uses the SQLAlchemy **legacy Query API** throughout data access layers. Key characteristics of the current state:

### Query Patterns in Use

| Pattern | Description |
|---|---|
| `session.query(Model)` | Base query construction returning a `Query` object |
| `session.query(Model).filter(...)` | Row filtering via `Query.filter()` / `Query.filter_by()` |
| `session.query(Model).all()` | Fetching all rows as a list of ORM instances |
| `session.query(Model).first()` | Fetching the first result or `None` |
| `session.query(Model).one()` | Fetching exactly one result or raising |
| `session.query(Model).one_or_none()` | Fetching one result or `None` |
| `session.query(Model).count()` | Counting rows via the Query interface |
| `session.query(Model).scalar()` | Returning a single scalar value |
| `session.query(Model).get(pk)` | Primary-key lookup via `Query.get()` |
| `session.query(Model).join(...)` | JOIN construction on the Query object |
| `session.query(Model).order_by(...)` | Ordering results |
| `session.query(Model).limit(...).offset(...)` | Pagination |
| `session.query(Model).options(...)` | Eager loading strategies (e.g., `joinedload`, `subqueryload`) |
| `session.query(Model).update(...)` | Bulk update via Query |
| `session.query(Model).delete(...)` | Bulk delete via Query |
| `session.query(func.count(...))` | Aggregate queries via Query |

### Result Consumption

Current code consumes `Query` results as plain lists of ORM model instances or tuples. The `Query` object is iterable and returns instances directly. This differs from `Session.execute()`, which returns a `Result` object requiring explicit unpacking (e.g., `.scalars()`, `.all()`, `.one()`).

## Proposed Changes

For each affected component, the legacy Query API call is replaced with a `select()` construct executed via `Session.execute()`.

### Component Change Table

| Component | Before | After | Breaking? |
|---|---|---|---|
| Basic model fetch | `session.query(Model)` | `session.execute(select(Model))` | N — internal change |
| Filter clause | `.filter(Model.col == val)` | `select(Model).where(Model.col == val)` | N |
| Filter by keyword | `.filter_by(col=val)` | `select(Model).filter_by(col=val)` | N |
| Fetch all rows | `.all()` | `.scalars().all()` on `Result` | **Y** — result type changes |
| Fetch first row | `.first()` | `.scalars().first()` | **Y** — result type changes |
| Fetch one row | `.one()` | `.scalars().one()` | **Y** — result type changes |
| Fetch one or none | `.one_or_none()` | `.scalars().one_or_none()` | **Y** — result type changes |
| Primary-key lookup | `session.query(Model).get(pk)` | `session.get(Model, pk)` | **Y** — method moves to Session |
| Count rows | `session.query(Model).count()` | `select(func.count()).select_from(Model)` executed via `session.execute(...).scalar()` | **Y** — query structure changes |
| Scalar value | `.scalar()` | `session.execute(...).scalar()` | N — equivalent |
| JOIN | `.join(Other, condition)` | `select(Model).join(Other, condition)` | N |
| ORDER BY | `.order_by(col)` | `select(Model).order_by(col)` | N |
| LIMIT / OFFSET | `.limit(n).offset(m)` | `select(Model).limit(n).offset(m)` | N |
| Eager loading | `.options(joinedload(...))` | `select(Model).options(joinedload(...))` | N |
| Bulk update (Query) | `.update({...}, synchronize_session=...)` | `session.execute(update(Model).where(...).values(...))` | **Y** — uses `update()` construct |
| Bulk delete (Query) | `.delete(synchronize_session=...)` | `session.execute(delete(Model).where(...))` | **Y** — uses `delete()` construct |
| Column-level query | `session.query(Model.col1, Model.col2)` | `session.execute(select(Model.col1, Model.col2))` with `.all()` (no `.scalars()`) | **Y** — result unpacking changes |
| Aggregate / func query | `session.query(func.count(Model.id))` | `session.execute(select(func.count(Model.id))).scalar()` | **Y** — result access changes |

### What Is Removed

- All direct instantiation or use of the `Query` class.
- All calls to `session.query(...)` as an entry point.
- Any subclassing or extension of `Query` (e.g., custom `Query` subclasses passed to `sessionmaker(query_cls=...)`).

### What Is Added

- Import and use of `select()`, `update()`, `delete()` from `sqlalchemy` (core constructs).
- Use of `Result.scalars()` for ORM instance extraction.
- Use of `session.get(Model, pk)` for primary-key lookups.

## Compatibility & Breaking Changes

| Breaking Change | Impact | Migration Path |
|---|---|---|
| `.all()` on `Query` returns `list[Model]`; `.execute().scalars().all()` also returns `list[Model]` but callers must add `.scalars()` | All call sites consuming query results | Add `.scalars()` before terminal method on all ORM single-entity queries |
| `session.query(Model).get(pk)` removed | All primary-key lookup call sites | Replace with `session.get(Model, pk)` |
| Column-tuple queries return `Row` objects, not plain tuples | Call sites unpacking multi-column results | Access columns by attribute name or positional index on `Row`; behavior is largely compatible but type annotations differ |
| Bulk `.update()` / `.delete()` on `Query` removed | Any call site performing in-place bulk mutations | Replace with `update()`/`delete()` core constructs executed via `session.execute()` |
| Custom `Query` subclass passed via `query_cls` to `sessionmaker` | Any custom query extensions | TODO — audit custom `Query` subclasses and determine equivalent extension points in the 2.0 API |
| `LegacyAPIWarning` suppression code | Any `warnings.filterwarnings` suppressing SQLAlchemy legacy warnings | Remove suppression; warnings should no longer be emitted after migration |
| `future=True` engine flag behavior | Session and engine configuration | TODO — confirm whether `future=True` is already set; if not, enabling it as part of this migration may surface additional behavioral differences |

## Acceptance Criteria

1. **Given** the full test suite is run, **when** SQLAlchemy deprecation warnings are configured as errors, **then** zero `LegacyAPIWarning` or `SADeprecationWarning` instances related to the Query API are raised.

2. **Given** any code module in the repository, **when** a static search for `session.query(` is performed across all source files, **then** zero matches are found.

3. **Given** any code module in the repository, **when** a static search for `Query` class imports from `sqlalchemy.orm` is performed, **then** zero matches are found (excluding test fixtures explicitly testing legacy compatibility, if any).

4. **Given** a database with known seed data, **when** each migrated query is executed via `Session.execute(select(...))`, **then** the returned rows match the rows previously returned by the equivalent `session.query(...)` call, verified by existing integration tests passing without modification to their assertions.

5. **Given** a primary-key lookup call site, **when** `session.get(Model, pk)` is called with a valid primary key, **then** the correct ORM instance is returned; when called with a non-existent key, `None` is returned — matching prior `session.query(Model).get(pk)` behavior.

6. **Given** a bulk update operation, **when** `session.execute(update(Model).where(...).values(...))` is called, **then** the affected rows are updated in the database and the session state is consistent, matching the behavior of the prior `Query.update()` call.

7. **Given** a bulk delete operation, **when** `session.execute(delete(Model).where(...))` is called, **then** the targeted rows are removed from the database, matching the behavior of the prior `Query.delete()` call.

8. **Given** the CI pipeline, **when** the full test suite executes, **then** all tests that previously passed continue to pass with no regressions introduced by this migration.

9. **Given** any aggregate query (e.g., count), **when** executed via `session.execute(select(func.count(...)))`, **then** the scalar result equals the value previously returned by the equivalent `session.query(func.count(...)).scalar()` call.

10. **Given** a multi-column `select()` query, **when** results are consumed, **then** column values are accessible by attribute name on the returned `Row` objects and match the values previously returned as tuple elements.
