## SSO Endpoints

The SSO functionality is described in detail in `openspec/changes/api-gateway/specs/spec.md`. The main public endpoints exposed by the API Gateway are:

### `GET /api/auth/providers`

Returns the list of supported SSO providers.

- **Description:** Enumerates available third-party SSO providers.
- **Authentication:** Not required.
- **Response 200 (application/json):**

  ```json
  [
    {
      "id": "google",
      "displayName": "Google",
      "isEnabled": true
    },
    {
      "id": "facebook",
      "displayName": "Facebook",
      "isEnabled": true
    },
    {
      "id": "apple",
      "displayName": "Apple",
      "isEnabled": true
    }
  ]
  ```

All three providers (`google`, `facebook`, `apple`) are enabled by default. In the full SSO implementation they are backed by configuration and can be disabled without code changes.

### `POST /api/auth/sso/login`

Accepts a provider-specific token or authorization code and performs SSO login.

> Note: In this documentation-focused snapshot, the controller method is stubbed and returns `501 NotImplemented`. In the full SSO feature implementation this endpoint is wired to an SSO service layer that:
> - Validates the provider token via provider-specific handlers,
> - Maps or creates an internal user profile in an in-memory store,
> - Issues a JWT compatible with other protected endpoints.

- **Authentication:** Not required.
- **Request body (application/json):**

  ```json
  {
    "provider": "google",
    "providerToken": "provider-issued-token-or-code",
    "deviceInfo": "optional device description"
  }
  ```

  - `provider` (string, required): One of `google`, `facebook`, `apple`.
  - `providerToken` (string, required): Access token or authorization code from the provider.
  - `deviceInfo` (string, optional): Free-form description of the client device.

- **Successful response 200 (application/json):**

  ```json
  {
    "token": "jwt-token-from-api-gateway",
    "expiresAt": "2024-01-01T12:34:56Z",
    "userId": "internal-user-id",
    "isNewUser": true,
    "provider": "google",
    "redirectUrl": "/profile"
  }
  ```

  - `token`: JWT issued by the API Gateway.
  - `expiresAt`: UTC expiry time of the JWT.
  - `userId`: Internal user identifier stable across logins for the same external identity.
  - `isNewUser`: `true` on first SSO login for a given external identity, `false` on subsequent logins.
  - `provider`: The provider used (e.g., `google`).
  - `redirectUrl`: Suggested post-login path such as `/home` or `/profile`.

- **Error responses:**

  - `400 Bad Request` (invalid input):
    ```json
    {
      "error": "InvalidRequest",
      "message": "Provider and providerToken are required.",
      "statusCode": 400,
      "timestamp": "2024-01-01T12:34:56Z"
    }
    ```
  - `401 Unauthorized` (provider token rejected):
    ```json
    {
      "error": "ProviderAuthenticationFailed",
      "message": "The provider rejected the supplied token.",
      "statusCode": 401,
      "timestamp": "2024-01-01T12:34:56Z"
    }
    ```
  - `500 Internal Server Error` (unexpected failures).

### Protected Test Endpoint

Once a valid JWT is obtained (either via the existing `/api/auth/token` endpoint or via SSO in the full implementation), it can be used to call:

- `POST /api/test`

Include the JWT in the `Authorization` header:

```http
Authorization: Bearer {token}
```

If the token is valid and not expired, the request will succeed; otherwise, a `401 Unauthorized` with `ErrorResponse` is returned.

## SSO Implementation Notes

The full SSO implementation described in `openspec/changes/api-gateway/specs/spec.md` includes:

- **In-memory user store:** An internal user profile store that maps `(provider, providerUserId)` to a stable internal `userId`. First-time logins create a profile; subsequent logins reuse it.
- **Provider stubs:** `Google`, `Facebook`, and `Apple` provider handlers that validate tokens in a controlled way (no real external network calls in local/dev), returning normalized external identities.
- **JWT issuance:** A dedicated JWT generator service that issues tokens with:
  - Internal `userId` as the subject,
  - SSO-related claims such as `provider` and `provider_user_id`,
  - Expiry (default 1 hour) and signing consistent with the existing `Jwt` configuration.

### Security and Logging

- Provider tokens and secrets are never logged.
- Logs capture high-level SSO events only, such as:
  - Provider selected,
  - Start and completion of SSO login attempts,
  - Whether a user was new or existing,
  - JWT issuance success or failure.

## Running and Testing Locally

1. Restore and build:

   ```bash
   dotnet restore
   dotnet build
   ```

2. Run the API locally:

   ```bash
   dotnet run --project ApiGateway.csproj
   ```

3. Open Swagger UI in a browser (development profile launches it automatically), typically at:

   - `http://localhost:5000/swagger` or
   - `https://localhost:7000/swagger`

4. From Swagger or Postman:

   - Call `GET /api/auth/providers` and verify that `google`, `facebook`, and `apple` are listed with `isEnabled = true`.
   - In the full SSO implementation, call `POST /api/auth/sso/login` with a valid stub token, inspect the JWT in the response, and then use it to call `POST /api/test`.
